# Scenity: from the resus room lab to a generic 3D scene editor and engine

Planning date: **2026-10-15**. Status: **draft for the owner** (the questions are in §11). §12 is the checklist, §13
the progress log.

**The aim.** Scenity becomes a 3D scene editor and engine for any scene and any simulation. A user makes a project,
imports models, builds scenes in the editor, adds time and behaviour, checks the result with rules, and ships a small
player. The resus room of CodeBlue becomes one plugin and one sample project on top of the engine. It is no longer the
engine.

**What stays.** The strong parts of today stay (§4): the worker renderer with WebGPU and WebGL, the deterministic frame
and its frame key, the command registry with a Claude tool for each command, proposals and ghosts, the workbench, the
asset pipeline with its rights gates, and the discipline of tests, gallery baselines and budgets.

**Scope.** The scenity repository (`~/Development/Snowpine/scenity`). The CodeBlue repository changes only in SE10-04,
when it moves to the Scenity packages.

**Sources.** Six read-only reviews of the code on 2026-10-15 (the 3D runtime, the editor app, the workbench, the asset
pipeline, the support packages, the timeline and content layer) and spot checks of their main claims. Appendix A has
the inventory per package. Appendix B lists the defects that the reviews found.

**Task IDs:** `SE<phase>-<nn>` (SE for Scenity Engine). Four tasks are architecture decisions (SE1-01, SE2-01, SE4-01,
SE6-01). Each of them writes a record `docs/adr/<nn>-<name>.md`.

## 1. Summary

**One rule for the whole engine: a frame is a pure function of data.** The data are the documents (project, scene,
prefab, sequence, rules), the override layers, the time and the plugin input. Scene data are never TypeScript
constants again. An editor save writes a document, never source code.

Four big changes:

1. **Data, not code.** Today the room is the TypeScript constant `WARD_ROOM_A`, the props are a closed union of 10
   slots, and "Save placement" rewrites number literals in `.ts` files. After this plan, a scene is a JSON document of
   entities with typed components, and the editor writes that document.
2. **An engine with plugins.** Today `Room3DCore.update()` is the resus choreography, and the renderer input
   `SceneInput` is `{ room, members, people, patient, devices }`. After this plan, the core runs any scene, and the
   resus room is a plugin that gives components, systems, a simulation, editor commands and tools.
3. **An editor over entities.** Today the selection is one of six kinds (`prop`, `device`, `member`, `patient`, `room`,
   `scratch`), and add or delete of a real object is a prompt to Claude. After this plan, the editor has a hierarchy, an
   inspector from component schemas, transform gizmos, an asset browser and real add, duplicate and delete.
4. **Time as data.** Today a take is a list of clinical events (`act`, `phase`, `patient`, `devices`, …) and a preset
   is a TypeScript function. After this plan, a sequence is a document of tracks and keys, and a simulation plugin
   gives the meaning of its action keys.

### 2.2 What is generic and good today

- **The renderer backends.** A clean `RenderBackend` interface with WebGL and WebGPU (`packages/room3d/src/core/render`),
  the WebGPU fixes for three r186, the GPU timer, KTX2 with a transcoder that runs under a strict CSP.
- **The worker host.** `createRoom3DRenderer` picks the OffscreenCanvas worker or the main thread; the protocol is
  plain data; the handler has an extension point; the clock anchors keep the worker in time with the page.
- **Adaptive quality.** `model/adapt.ts` is pure: render scale, then tier, then still poses, then the 2D fallback.
- **Asset integrity.** Same origin only, and size and SHA-256 checks before parse (`core/assets.ts`).
- **Character parts.** The neutral IK body (`core/body.ts`), the rig driver, the clip sampler and the clip layer, the
  pose blend (`choreo/poseMix.ts`), the path planner (`model/path.ts`) and the timed walk.
- **Determinism.** No wall clock and no random in the model and the core; the frame key (`labs-platform/frameKey.ts`)
  names one picture; `labStateAt` replays events with 1 s checkpoints.
- **The editor machinery.** 69 commands in a registry with argument specs, selection rules and `when` conditions; the
  runner with owner, Claude and script callers; proposals with ghosts; the undo history; the palette (⌘P); snap,
  measure, groups, hide and solo, onion skin, split panes, the timeline, the frame index, compare and graph views.
- **The lab tools.** The render pool with warm browser pages, `shot`, `sheet`, `clip`, `bench`, `verify`, `parity`.
- **The workbench.** A token-guarded Bun host, terminals, the Agent SDK chat, Git with a safe allowlist, per-turn
  snapshots, the Changes tab, runs, loops with a stop gate, a frame index and a postMessage bridge to the frame.
- **The asset pipeline.** glTF-Transform and meshoptimizer, deterministic KTX2 (ETC1S and UASTC), two LOD tiers, a build
  cache, a pinned Blender (local or Docker) with a byte compare of exports, a drop import for glb, gltf, fbx, obj and
  blend, a rights record per asset, a licence register and a release gate.

### 2.3 What ties the code to the resus room (ranked)

1. **The scene is TypeScript, and saves rewrite source code.** `WARD_ROOM_A` (`model/room.ts:172`), the closed
   `PropSlot` union (`model/manifest.ts:71`), 115 `tunable()` calls. "Save placement" runs `labs tune-apply`, which
   rewrites number literals in `packages/room3d/src/**` (`apps/editor/scripts/lab/tuneApply.ts`). `camera-save`
   rewrites the `CAMERAS` literal. Add, delete and promote of a prop are prompts for Claude to edit about six files.
2. **The renderer input is a resus contract.** `SceneInput { room, members, people, patient, devices }`
   (`model/types.ts:373`). `Activity` is a closed union of nine clinical activities. `DeviceInput` is a fixed set of
   booleans (monitor, defib, pads, SpO2, …). The lab fakes the CodeBlue engine and goes through the CodeBlue contract
   views (`room3d-view/src/input.ts`).
3. **The frame update is resus choreography.** `Room3DCore.update()` (`core/room3dCore.ts:1454-2013`): bed release,
   shock tracking, CPR memory, step stool, team places, intubation, patient pose, paddles, bystanders, screens.
4. **The clip family enum comes from the CodeBlue engine.** `ClipFamily` comes from
   `model/generated/webPresentation.ts` (written by `codeblue content presentation`). It types the 25 pose families,
   the manifest, the clip layer and `memberPose`.
5. **Closed asset unions and one rig.** `PropSlot`, `DeviceSlot`, `npcIds`, `patients[0]`, the clip families
   `patient_cpr` and `patient_shock`, the rig `codeblue_humanoid_v1` (UE5 bone names). The runtime refuses any other
   rig and any other slot.
6. **The lab core reads resus internals.** `LabsCore` reads `frameMemory { cpr, cprSim, bedRelease }`, the patient
   paddle sites, the paddle props and the patient model. `PickKind` includes `patient`; `pick.ts` has a regex of device
   names.
7. **The editor holds domain modules.** About 20 files in `apps/editor/src/lab/editor` are resus rules: hand targets,
   cables, team places, reach pairs, layout metrics and limits ("clinical reviewer"), the words for placement by text.
   `lab.ts` (1,565 lines) has 78 presets.
8. **The workbench host knows the lab.** The `"lab"` surface literal (33 places in the page), a copy of the lab API
   call names, the `labs` CLI allowlist, file maps of pose families, `PLACEMENT_PATHS`, the resus context packet.
9. **Hard-coded repo paths.** `CONTENT_ROOTS`, `ASSET_MANIFEST` and `FAMILIES_DIR` in `labs-platform`; `art/room3d` and
   `packages/room3d-view/src/assets` in the asset tools; `apps/web`, `apps/console` and `engine/` (not in this repo).
10. **Names and the support chain.** The CodeBlue SDK (`api-client`, `sdk-core`, `voice`, `vue`) starts in the editor
    `main.ts`; the runtime clock lives in the patient monitor package; `CODEBLUE_*` variables, `codeblue.*` keys, the
    `resus` theme and the `--cb-` tokens.

### 3.2 The documents

All documents are JSON with a `format` field and a version. The canonical writer sorts the keys, rounds numbers to a
grid and uses two spaces, so a change gives a small diff. A schema in zod gives the types, the checks and a JSON Schema.
Units are metres, Y is up, and the axes are right-handed, as in glTF.

**The project** (`scenity.project.json`):

```json
{
  "format": "scenity.project/1",
  "id": "showroom",
  "name": "Showroom",
  "scenes": ["scenes/main.scene.json"],
  "sequences": ["sequences/tour.sequence.json"],
  "assets": ["assets"],
  "plugins": ["./plugins/doors"],
  "rules": ["rules/layout.rules.json"],
  "quality": { "budgets": { "scene": { "high": { "triangles": 400000, "bytes": 22000000 } } } },
  "workbench": {
    "surfaces": [{ "id": "editor", "kind": "scene", "label": "Editor" }],
    "runs": { "check": "scenity check" }
  }
}
```

**The scene** (`*.scene.json`). `entities` is a map by ID, so a JSON Pointer reaches each value
(`/entities/cart/components/transform/position/0`). `parent` and `index` give the tree.

```json

  "entities": {
    "cart": {
      "name": "Cart",
      "parent": null,
      "index": 0,
      "tags": ["movable"],
      "components": {
        "transform": { "position": [0.85, 0, -1.45], "rotation": [0, -0.115, 0, 0.993], "scale": [1, 1, 1] },
        "model": { "asset": "asset:01J9Z6Q3R9" },
        "obstacle": { "footprint": "bounds" },
        "socket": { "points": { "top": [0, 0.92, 0] } }
      }
    },
    "lamp": {
      "parent": "cart",
      "index": 0,
      "components": {
        "transform": { "position": [0, 0.92, 0] },
        "light": { "type": "point", "intensity": 2, "colour": [255, 236, 210], "range": 4, "shadow": false }
      }
    },
    "front": {
      "parent": null,
      "index": 1,
      "components": { "transform": { "position": [0, 1.6, 3] }, "camera": { "fov": 45, "target": [0, 1, 0] } }
    }
  },

```

**An override layer** (`*.overrides.json`): a list of ops on top of a scene. Layout variants, per-pane values, URL
values and proposals are override layers.

```json
{
  "format": "scenity.overrides/1",
  "scene": "main",
  "ops": [{ "op": "set", "path": "/entities/cart/components/transform/position/0", "value": 0.9 }]
}
```

### 3.3 The runtime pipeline

```text
documents (project, scene, prefabs) + override layers ─┐
sequence + time t ─────────────────────────────────────┼─► evaluate() ─► frame state ─► systems (plugins) ─► presenters ─► renderer
plugin input (a live engine, a recorded stream) ───────┘   pure; checkpoints       pure per frame,        three.js objects  (worker or
                                                            for seek                memory saved for seek                    main thread)
```

- `evaluate()` lives in `@scenity/scene`. It is pure. It applies the override layers, samples the tracks at time t and
  reduces the action keys through the simulation plugins. Checkpoints make a seek fast (today's `labStateAt`).
- **Systems** run each frame in the core. They read the frame state and write presenter outputs: transforms, poses,
  visibility and material values. A system can keep memory from frame to frame (today: CPR memory, shock tracking), but
  the memory has save and restore, so a seek gives the same frame as playback.
- **Presenters** turn components into three.js objects: one presenter for each component type.
- The page sends the documents once, ops for each edit, and the plugin input when it changes. The worker never gets a
  full scene again for a small edit.

### 3.4 Plugins

A plugin has up to five faces. The project config lists the plugins. The build bundles them (a Vite virtual module), so
no code loads from a URL at run time.

| Face       | API                                                                                         | Runs in                    | Resus example                                          |
| ---------- | ------------------------------------------------------------------------------------------- | -------------------------- | ------------------------------------------------------ |
| Runtime    | `defineRuntimePlugin`: components, systems, presenters, input schema, debug layers, metrics | Render worker or main      | Patient, team poses, devices, screens, bed recline     |
| Simulation | `defineSimulation`: state schema, initial, reduce, settle, project                          | Page (pure)                | The fake engine of `lab.ts`: phases, shock, CPR holds  |
| Editor     | `defineEditorPlugin`: commands, panels, inspector widgets, browser tabs, overlays           | Editor page                | Team, Patient and Devices tabs; cable and hand handles |
| Host       | `defineHostPlugin`: tools, runs, context lines, file maps                                   | Workbench host (Bun)       | `lab_where`, `lab_check`, `lab_inspect`                |
| Assets     | `defineAssetPlugin`: importers, checks, approval roles                                      | Asset tools (Bun, Blender) | UE5 importers, the clinical review of clips            |

A sketch of the runtime face:

```ts
export default defineRuntimePlugin({
  id: "resus",
  components: [patientComponent, memberComponent, deviceComponent],
  input: resusInputSchema, // today's SceneInput
  systems: [resusRoomSystem], // first the old ResusRoomCore.update (SE3-09), then smaller systems (SE10-02)
  presenters: { "resus.patient": patientPresenter },
  debugLayers: [paddleSitesLayer],
  metrics: [handsToSternum, maskHandToMask, paddlesToPads],
});
```

A project can hold its own plugins (`<project>/plugins/*`). In dev, a change of plugin code reloads the worker.

## 4. Rules that stay

1. **A frame is a pure function of its inputs.** The same documents, overrides, sequence, time and plugin input give
   the same frame. The frame key names one picture, and a URL still shows one exact frame.
2. **Every edit is an op.** Every op has an inverse. Nothing commits by itself, and the Changes tab shows each change
   as a diff.
3. **Every editor action is a command with a Claude tool.** Claude proposes and the owner accepts. Only the owner's
   switch of the session lets Claude apply at once.
4. **A player build holds no editor and no dev code** (the marker gate, today's `tools/lab-markers.ts`).
5. **The renderer runs in a worker when it can.** WebGPU is the default; WebGL is the kill switch; a failure goes from
   WebGPU to WebGL and from the worker to the main thread.
6. **Assets are checked.** Size and SHA-256 before parse, budgets per tier, a rights record and the licence register
   before a release.
7. **Builds are reproducible.** A pinned Blender, a byte compare of the outputs.
8. **Budgets.** Size budgets per entry; at most 500 lines per file and 80 lines per function (`tools/room3d/shape.ts`).
9. **Conventions.** Code comments in ASD-STE100 Simplified Technical English; no AI attribution in commits; the owner
   commits and pushes.
10. **No engine package names a domain** (the domain word lint, SE1-02).

## 5. Strategy: change with no break

- **Strangler, not rewrite.** Each task moves or wraps working code. The resus room works after every task.
- **The parity suite is the gate** (SE0-04). A task that changes a resus frame needs the owner's approval of the new
  baselines, as today.
- **Two users for each generic feature.** A generic feature is done only when the resus plugin and one non-medical
  sample use it. This stops a design that fits only the resus room, and it stops features that nobody uses.
- **First generic over the input type, then the document.** SE1 makes the runtime generic over its input type with no
  data change. SE2 and SE3 add the documents. Thus the large moves of files (SE1) and the new model (SE2, SE3) are not
  in the same change.
- **A spike before the large split.** The first slice (§7.2) renders a small document scene with a minimal builder, so
  the document model meets real art before SE1-06 and SE1-07 move about 40,000 lines.
- **Converters for the old data.** Scripts write the old TypeScript data (`WARD_ROOM_A`, `CAMERAS`, the takes, the
  moments, the checks) as documents. An old module goes only when its converted data give the same frames.
- **Old names stay as aliases for one phase:** the Claude tools `lab_*`, `__room3dLab`, `bun run labs`, the `CODEBLUE_*`
  variables.

## 10. Non-goals

- Real-time editing by more than one user.
- A visual (node) scripting editor and a node graph for materials. The material editor of SE5-12 edits values.
- A native runtime. Scenity is web-first (three.js, WebGPU and WebGL); other engines get glTF (SE9-06).
- Multiplayer and network play.
- XR in this plan. WebXR can come later; `threeDiet` removes the three.js XR code today.
- Code that loads from a URL at run time. Plugins are bundled at build time.
- An editor for phones. The player runs on phones; the editor is for desktop browsers.
